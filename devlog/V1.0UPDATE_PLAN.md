# V1.0 UPDATE PLAN: AI 댓글 생성 시스템 개편

## 개요

리뷰 유형을 먼저 분류(호감/반감 > 컴플레인/클레임)한 후, 각 유형에 맞는 가이드라인 기반 답변 3종을 생성하도록 AI 댓글 시스템을 전면 개편한다.

### 현재 문제점

| 항목 | 현재 | 문제 |
|------|------|------|
| 리뷰 분류 | 없음 | 호감/반감 구분 없이 동일 프롬프트로 생성 |
| 답변 스타일 | empathy/guidance/apology 고정 | 리뷰 유형과 무관하게 항상 3종 동일 스타일 |
| 가이드라인 활용 | Guideline.md 미반영 | 프롬프트에 가이드라인 전략이 포함되지 않음 |
| 프롬프트 | 단일 system prompt | 유형별 맞춤 전략 부재 |

### 개편 목표

```
[리뷰 입력]
    |
    v
[1단계: 유형 분류] ── Gemini API 호출
    |
    ├── 호감 리뷰 (positive)
    |       └── 감사+공감+재방문 전략 기반 답변 3종 생성
    |
    └── 반감 리뷰 (negative)
            |
            ├── 컴플레인 (complaint) ── 주관적 불만
            |       └── YES-BUT (공감+정제된 해명) 전략 기반 답변 3종 생성
            |
            └── 클레임 (claim) ── 객관적 사실 기반
                    └── YES-BUT (사과+책임+개선) 전략 기반 답변 3종 생성
```

## Phase 1: 리뷰 유형 분류 시스템 구축

### 1-1. 분류 체계 정의

리뷰를 3가지 유형으로 분류한다:

| 유형 코드 | 한글명 | 설명 | 예시 |
|-----------|--------|------|------|
| `positive` | 호감 리뷰 | 만족, 칭찬, 감사 표현 | "원장님이 친절하고 시술도 만족스러워요" |
| `complaint` | 컴플레인 | 주관적 감정/기대치 미달 불만 | "비용이 너무 비싸요", "불친절해요" |
| `claim` | 클레임 | 객관적 기준/약속 위반 문제 | "예약했는데 1시간 대기", "시술 부작용" |

### 1-2. DB 스키마 변경

**파일**: `backend/models.py`, `backend/schemas.py`

`reviews` 테이블에 분류 결과 컬럼 추가:

```python
# models.py - Review 모델에 추가
review_type = Column(String(20), nullable=True)        # "positive", "complaint", "claim"
review_type_reason = Column(Text, nullable=True)        # 분류 근거 (AI가 제공)
```

```python
# schemas.py - ReviewOut에 추가
review_type: str | None = None
review_type_reason: str | None = None
```

### 1-3. 분류 전용 AI 함수 구현

**파일**: `backend/services/gemini.py`

새 함수 `classify_review()` 추가:

```python
async def classify_review(review_content: str, review_rating: float) -> dict:
    """
    리뷰를 호감/컴플레인/클레임으로 분류한다.
    Returns: {"type": "positive|complaint|claim", "reason": "분류 근거"}
    """
```

**분류 전용 시스템 프롬프트**:

```
당신은 병원 리뷰 분류 전문가입니다.
환자가 남긴 리뷰를 분석하여 아래 3가지 유형 중 하나로 분류하세요.

## 분류 기준

1. positive (호감 리뷰): 만족, 칭찬, 감사를 표현하는 리뷰
2. complaint (컴플레인): 주관적인 감정이나 기대치 미달에 의한 불만
   - 예: 불친절함, 비싼 비용, 분위기 불만 등
3. claim (클레임): 객관적인 기준이나 약속 위반으로 발생한 문제
   - 예: 예약 미준수, 시술 부작용, 잘못된 진료, 위생 문제 등

## 판단 보조 정보
- 별점이 높더라도(4-5점) 내용에 불만이 있으면 내용 기준으로 분류
- 별점이 낮더라도(1-2점) 내용이 긍정적이면 내용 기준으로 분류
- 내용이 없거나 모호한 경우 별점 기준 (4점 이상 positive, 3점 이하 complaint)

결과를 반드시 아래 JSON 형식으로만 출력하세요:
{"type": "positive|complaint|claim", "reason": "분류 근거를 한 문장으로"}
```

### 1-4. 분류 호출 시점

분류는 **댓글 생성 요청 시** 수행한다 (리뷰 수집 시가 아님 - API 호출 최소화):

- 수동 생성: `POST /api/reviews/{id}/generate-comments` 호출 시
- 자동 생성: `automation_service.py`의 `process_auto_reply()` 내

분류 결과는 `reviews` 테이블에 저장하여 재분류 방지.

### 2-1. 프롬프트 구조 재설계

**파일**: `backend/services/gemini.py`

단일 system prompt를 유형별 3개 프롬프트로 분리한다.

#### 공통 규칙 (모든 유형에 적용)

```
## 공통 규칙
- 한국어로 작성
- 100~150자 내외
- 개인정보나 의료 정보는 포함하지 않기
- {reviewer}는 리뷰 작성자 이름으로 치환됨
- {hospital}은 병원명으로 치환됨
```

#### 유형별 프롬프트

**positive (호감 리뷰) 프롬프트**:

```
당신은 병원 리뷰 답변 전문가입니다. 아래는 만족/칭찬을 담은 호감 리뷰입니다.

## 작성 전략
1. 감사 인사: 방문 및 소중한 리뷰에 대한 감사 표현
2. 포인트 강조: 고객이 언급한 장점(친절, 실력, 시설 등)을 한 번 더 언급
3. 재방문 기약: 다음 만남을 기약하며 앞으로의 다짐을 밝힘

## 톤 & 핵심
- 공감과 감사 표현 중심
- 리뷰에 나타난 병원의 서비스와 치료에 대한 구체적인 칭찬 포인트를 답글의 주요 소재로 활용
- 따뜻하고 진심 어린 어조

{공통 규칙}

3가지 변형 답변을 생성하세요. 각 답변은 같은 전략을 따르되 표현과 강조점을 다르게 합니다:
1. 변형A: 감사 중심 - 리뷰 감사에 무게
2. 변형B: 칭찬 강조 - 고객이 언급한 장점을 구체적으로 재언급
3. 변형C: 재방문 유도 - 앞으로의 다짐과 재방문 기약에 무게
```

**complaint (컴플레인) 프롬프트**:

```
당신은 병원 리뷰 답변 전문가입니다. 아래는 주관적 불만을 담은 컴플레인 리뷰입니다.

## 작성 전략: YES - BUT 구조
- YES (언어/감정 복사): 고객이 제시한 문제를 요약하고, 느꼈을 감정에 공감 표현
- BUT (정제된 해명): 오해가 있었던 상황이나 어쩔 수 없었던 배경을 정중하게 설명

## 톤 & 핵심
- 고객의 감정을 먼저 긍정하고 수용
- 정제된 언어로 병원의 입장 설명 및 개선 의지 표명
- 변명이 아닌 설명의 톤

{공통 규칙}

3가지 변형 답변을 생성하세요. 각 답변은 YES-BUT 구조를 따르되 강조점을 다르게 합니다:
1. 변형A: 공감 중심 - YES 부분에 무게, 감정 공감 강조
2. 변형B: 해명 중심 - BUT 부분에 무게, 합리적 설명 강조
3. 변형C: 개선 약속 - 향후 개선 의지와 구체적 방안에 무게
```

**claim (클레임) 프롬프트**:

```
당신은 병원 리뷰 답변 전문가입니다. 아래는 객관적 사실 기반의 클레임 리뷰입니다.

## 작성 전략: YES - BUT 구조
- YES (언어 복사/사과): 문제를 즉시 인정하고 진정성 있는 사과 및 상황 설명
- BUT (책임감/개선 약속): 재발 방지를 위한 구체적인 대책과 개선 의지 강조

## 톤 & 핵심
- 즉각적이고 진정성 있는 사과
- 문제 회피 없이 책임 인정
- 구체적인 재발 방지 대책 제시
- 무거운 마음을 표현하되 과도한 비굴함은 지양

{공통 규칙}

3가지 변형 답변을 생성하세요. 각 답변은 YES-BUT 구조를 따르되 강조점을 다르게 합니다:
1. 변형A: 사과 중심 - 진심 어린 사과와 상황 인정에 무게
2. 변형B: 원인 설명 - 문제 발생 배경과 경위 설명에 무게
3. 변형C: 개선 대책 - 구체적 재발 방지 대책과 시스템 개선에 무게
```

## Phase 4: API 라우터 수정

### 4-1. 댓글 생성 엔드포인트 수정

**파일**: `backend/routers/comments.py`

`POST /api/reviews/{review_id}/generate-comments` 흐름 변경:

```
기존: review 조회 → generate_comments() → 저장 → 반환
변경: review 조회 → classify_review() → review_type 저장
                   → generate_comments(review_type=...) → 저장 → 반환
```

응답에 분류 결과 포함:

```json
{
  "review_type": "complaint",
  "review_type_reason": "비용에 대한 주관적 불만 표현",
  "comments": [
    {"id": 1, "style": "comp_empathy", "style_label": "공감 중심", "content": "..."},
    {"id": 2, "style": "comp_explain", "style_label": "해명 중심", "content": "..."},
    {"id": 3, "style": "comp_improve", "style_label": "개선 약속", "content": "..."}
  ]
}
```

### 4-2. 수동 유형 변경 엔드포인트 추가

관리자가 AI 분류 결과를 수정하고 재생성할 수 있는 엔드포인트:

```
PATCH /api/reviews/{review_id}/review-type
Body: {"review_type": "claim"}
```

이후 다시 `POST /api/reviews/{review_id}/generate-comments`를 호출하면 변경된 유형으로 재생성.

## API 호출 비용 고려

| 작업 | Gemini 호출 수 | 비고 |
|------|---------------|------|
| 리뷰 분류 | 1회 | 짧은 프롬프트, 빠른 응답 |
| 답변 생성 | 1회 | 유형별 프롬프트 적용 |
| **합계** | **2회/리뷰** | 기존 1회 대비 1회 추가 |

분류와 생성을 1회 호출로 합칠 수도 있으나, 분류의 정확도와 프롬프트 명확성을 위해 **2회 분리 호출을 권장**한다. 분류 호출은 토큰 사용량이 적어 비용 영향 미미.
